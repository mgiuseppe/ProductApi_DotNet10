# EF Core

- ORM used to map db tables to C# Entities.
- Migrations are editable while local and forward-only once pushed (see [Migrations](#migrations) and [ADR-0010](adr/0010-migrations-editable-until-pushed.md)).
- We will use IReadOnlyList and not IEnumerable to avoid a lazy query execution that would throw an ObjectDisposedException 
- We will use Fluent API (classes implementing IEntityTypeConfiguration inside infrastructure) to map EF against the entities withouth writing EF-related code inside Domain.
- a DBContext is not ThreadSafe and is designed to be used a single Unit Of Work (Scoped lifetime is the way, Also Repositories should be Scoped)
- Repositories will be implemented as collections and UoW will be in DbContext, because when a use case touches multiple repositories, the commit shouuld still be a single operation since no single repository "owns" SaveChanges  

- Generate migration and apply
```bash
dotnet ef migrations add InitialCreate --project src/Infrastructure --startup-project src/Api
dotnet ef database update --project src/Infrastructure --startup-project src/Api
```
- Note: InitialCreate is just the name of the migration, so you can add more migrations by specifying a different name
- Generate next migrations

## Persistence
- SQL Server (Azure SQL in the cloud) with snake_case names (`EFCore.NamingConventions`): raw SQL such as check constraints must use the snake_case column names (`discount_amount >= 0`).
- `decimal` is `decimal(18,2)`, `Guid` is `uniqueidentifier`, `DateTime` is `datetime2`: it has no time zone, so the domain normalizes incoming dates to UTC (`Voucher.Create`) and a converter in `AppDbContext.ConfigureConventions` marks every date read back as UTC.
- Strings without a max length become `nvarchar(max)`: give enum-as-string columns a max length (`orders.status`).
- Default collation is case-insensitive: string equality in LINQ ignores case.
- `EnableRetryOnFailure` retries transient errors (Azure SQL serverless resuming from a pause). A transaction opened by our code would need `Database.CreateExecutionStrategy()`; none exists today.
- Unique violations (errors 2601/2627, e.g. the same voucher redeemed by two orders concurrently) become a `ConflictException` (409) in `AppDbContext.SaveChangesAsync`.
- Ids are generated in the domain (`ValueGeneratedNever`).

## Migrations

### Two phases

| Phase | Rule |
|---|---|
| **Local** (not pushed yet) | Edit freely: `dotnet ef migrations remove`, regenerate, merge several into one, roll back the local database with `dotnet ef database update <PreviousMigration>` or reset it with `docker compose down -v`. |
| **Shared** (on `origin/main`) | Forward-only: never edit or delete the migration, never run `Down` against a shared database. A mistake is fixed with a new migration. |

`Down` stays as generated by EF: it is what makes local rollback work. Forward-only is enforced by process (the migrator only moves forward, the pipeline never targets an earlier migration), not by making `Down` throw.

With GitHub Flow the boundary will move from the push to the merge on `main`, and the checks below will become required CI checks.

### Backward compatibility (high availability only)

This project does **not** apply it ([ADR-0010](adr/0010-migrations-editable-until-pushed.md)): it has no high-availability requirement, so a breaking change goes out in one release with a short downtime (e.g. a single `RenameColumn`). The rest of this section describes what an app with zero-downtime deployments would need.

During a rolling update, and after a rollback of the image, the **previous version of the app runs on the new schema**. Every migration must leave a schema that works for both the current and the previous version. Changes that break this are split into several releases with **expand/contract**: add the new shape, move the code, remove the old shape in a later release.

How many releases depends on the deployment:
- **Versions overlap** (several instances, zero downtime): the previous version keeps writing only the old shape during the rollout, so the new version must not read data that only it writes until a second backfill.
- **No overlap** (single instance stopped then started, or a maintenance window): the new version can read the new shape right away. One release less.
- A database **trigger** that copies old to new during the transition removes the overlap problem without extra code in the app.

### Changes that need attention

A reference, not a procedure: in this project they are allowed in a single release, accepting the downtime. The "Usual approach" column is what a high-availability app would do. The `/verify-and-commit` skill lists them before a push as information, so that data loss (e.g. a rename scaffolded as drop + add) does not go unnoticed.

| Change | Why it is risky | Usual approach |
|---|---|---|
| `DropColumn`, `DropTable` | The previous version still reads or writes it | Release 1: stop using it (make it nullable or give it a default first, or inserts fail). Release 2: drop. |
| `RenameColumn`, `RenameTable` (EF scaffolds them when a property or entity is renamed) | The previous version uses the old name; if EF does not detect the rename it scaffolds drop + add and the data is lost | Expand/contract: add the new column, backfill, write both, switch reads, stop writing the old one, drop it. Or a trigger. Or a single rename when downtime is acceptable. |
| `AlterColumn` changing type, length or precision | Data can be truncated or the conversion can fail; the previous version may write values that no longer fit | New column with the new type plus backfill, as for a rename |
| `AlterColumn` from nullable to `NOT NULL` | Fails on existing nulls; the previous version may still insert nulls | Backfill first, switch to `NOT NULL` only when no running version writes nulls |
| `AddColumn` with `nullable: false` and no default | The previous version does not know the column, so its inserts fail | Add it nullable or with a default; tighten it in a later release |
| Unique index or constraint (`unique: true`, `AddUniqueConstraint`) | Fails on existing duplicates; the previous version may insert duplicates. In this project `AppDbContext` maps **every** unique violation to the voucher `ConflictException` | Check for duplicates first; revisit the `ConflictException` mapping |
| Foreign key or check constraint (`AddForeignKey`, `AddCheckConstraint`) | Fails on existing rows that violate it; the previous version may write violating rows | Clean the data first; add the constraint when every running version respects it |
| `migrationBuilder.Sql(...)` with `UPDATE`, `DELETE` or DDL | Long locks on large tables, no automatic `Down`, effects outside what EF tracks | Keep it idempotent, batch large updates, review the generated SQL with `dotnet ef migrations script` |
| Index on a large table | `CREATE INDEX` blocks writes while it builds | `migrationBuilder.Sql("CREATE INDEX ... WITH (ONLINE = ON)")`, available on Azure SQL (and SQL Server Enterprise/Developer) |
| MongoDB document shape (outside EF): renaming `OrderHistoryEntry` types, the `type` discriminator or fields | Existing documents no longer deserialize; there are no migrations to catch it | Keep reading the old shape (aliases, optional fields) or migrate the documents with a script |

Safe in general: `CreateTable`, `AddColumn` nullable or with a default, non-unique index on a small table, dropping an index the code does not rely on.

### Before every push

Run by `/verify-and-commit`:
1. **Shared migrations untouched** (blocks the push): no file under `src/Infrastructure/Migrations/` that exists on `origin/main` is modified or deleted, except `AppDbContextModelSnapshot.cs`, which EF updates with every new migration.
2. **No forgotten migration** (blocks the push): `dotnet ef migrations has-pending-model-changes --project src/Infrastructure --startup-project src/Api`.
3. **Changes that need attention** (information only): the new migrations are scanned for the operations in the table above and listed in the report, with a warning when data can be lost.
